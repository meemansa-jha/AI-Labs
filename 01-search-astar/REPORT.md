## Task 0 — Understand the Search Problem

A search problem is `P = (S, A, T, s0, G, c)`. For the warehouse:

| Component | Specification |
|-----------|---------------|
| **State `S`** | A grid cell the robot can occupy, written `(row, col)`. The state space is the set of all non-obstacle cells. |
| **Actions `A`** | `{Up, Down, Left, Right}` — move one cell in a cardinal direction. |
| **Transition `T`** | `T((r,c), a) = (r+dr, c+dc)` where `(dr,dc)` is the offset for action `a`, **defined only if** the target cell is on the grid and not a `#`. |
| **Initial state `s0`** | the cell marked `S`. |
| **Goal `G`** | the single cell marked `G`; the goal test is `state == goal`. |
| **Cost `c`** | every move costs `1`, so path cost = number of moves. |

**(a) What information is necessary to specify a state?**
Only the robot's position `(row, col)`. The warehouse layout is static and shared by every state, so it is part of the *problem*, not part of the *state*. There is nothing else that changes as the robot moves (no fuel, no carried items), so position is a complete description.

**(b) What makes an action invalid?**
An action is invalid if the destination cell is off the grid or is an obstacle `#`. These actions are simply not generated, so the robot can never occupy an illegal cell.

**(c) Is this a deterministic search problem?**
Yes. Each action from a given state leads to exactly one known successor; there is no randomness or uncertainty in the outcome of a move.

**(d) What would constitute a solution?**
A sequence of actions (equivalently, a sequence of adjacent free cells) starting at `S` and ending at `G`. An *optimal* solution is one of minimum total cost, i.e. the fewest moves.

## Task 1 — Plan the Agent (design, written before any code)

1. **State representation:** a Python tuple `(row, col)`.
2. **Warehouse representation:** a list of strings (one per grid row); a helper `passable()` tests bounds and the `#` symbol.
3. **Valid actions:** generated by trying all four offsets and keeping only those whose target cell is passable.
4. **Goal recognition:** compare the current state tuple with the stored goal tuple.
5. **Frontier contents:** for A\*, a priority queue of entries `(f, tie_breaker, state)` plus side tables `g_score[state]` (best cost so far) and `came_from[state]` (parent pointer). The tie-breaker is an increasing counter so equal-`f` nodes never force a comparison of raw states.
6. **Path reconstruction:** follow `came_from` back from the goal to the start, then reverse.

**Termination report (minimum):** whether a solution was found, the solution path, the path length, and the number of states expanded. The code reports all four (`SearchResult`).

## Task 4 — Inspect the A\* algorithm

| Concept | Where it appears in `warehouse_search.py` |
|---------|-------------------------------------------|
| State | `(row, col)` tuples throughout |
| Action | the `MOVES` dict and `Warehouse.neighbours()` |
| Transition | `nxt = (r+dr, c+dc)` inside `neighbours()`, filtered by `passable()` |
| Goal test | `Warehouse.is_goal()` |
| `g(n)` | `g_score[state]`; updated as `tentative_g = g_score[current] + 1` |
| `h(n)` | the `heuristic(state, goal)` call (default `manhattan`) |
| `f(n)` | `tentative_g + heuristic(nxt, goal)`, the first element of each frontier entry |
| Frontier | the `heapq` priority queue `frontier` |
| Visited states | `g_score` doubles as the closed test: a popped node is skipped if a cheaper `g` was recorded after it was queued |
| Path reconstruction | `_reconstruct()` following `came_from` |

**(a) What data structure is used for the A\* frontier?** A binary min-heap (`heapq`) — a priority queue ordered by `f`.

**(b) How does the program select the next state to expand?** `heapq.heappop` returns the frontier entry with the smallest `f = g + h`; ties are broken by an insertion counter.

**(c) Where is the heuristic calculated?** In the `heuristic(...)` function (Manhattan by default), called when pushing each neighbour and when checking for stale entries.

**(d) Does the program explicitly calculate `f(n) = g(n) + h(n)`?** Yes — `tentative_g + heuristic(nxt, goal)` is exactly `g + h`, and that value is the key the heap is ordered on.

**(e) How does the program prevent unnecessary repeated exploration?** A neighbour is only pushed (or re-pushed) when `tentative_g` improves on the best `g` recorded in `g_score`. When a node is popped, if its stored `g` is already better than the `g` implied by this heap entry, the entry is a stale duplicate and is skipped. This is a standard, correct A\* with lazy deletion.

## Task 5 — A\* vs blind search (BFS)

Measured on two maps. The original lab map is essentially a single corridor, so both algorithms must walk the same cells; an extra open two-room map makes the difference visible.

**Original (corridor) map**

| Measure | BFS | A\* |
|---|:--:|:--:|
| Solution found | yes | yes |
| Path length | 40 | 40 |
| States expanded | 64 | 64 |

**Open two-room map** (`maps.OPEN_WAREHOUSE`)

| Measure | BFS | A\* |
|---|:--:|:--:|
| Solution found | yes | yes |
| Path length | 23 | 23 |
| States expanded | **159** | **125** |

**(a) Did both algorithms find a solution?** Yes, on both maps.
**(b) Did they find paths of the same length?** Yes — both are optimal on a unit-cost grid, so both return length 40 / 23.
**(c) Which algorithm expanded fewer states?** A\* — equal on the corridor (no freedom to do better), but 125 vs 159 on the open map.
**(d) Why might A\* expand fewer states?** BFS is uninformed: it expands outward uniformly in all directions, including away from the goal. A\*'s `h(n)` term biases expansion toward cells that look closer to the goal, so it skips much of the region that leads away from `G`. On the corridor there is only one direction to go, so the heuristic has nothing to prune and the counts coincide.

## Task 6 — Investigate the heuristic

**Why is Manhattan distance appropriate here?** The robot moves only horizontally and vertically, one cell per step, at cost 1. The minimum number of such moves between two cells *ignoring walls* is exactly `|Δrow| + |Δcol|` — the Manhattan distance. Because walls can only make the true path longer, Manhattan never over-estimates the real cost, i.e. it is **admissible** (`h ≤ h*`). It is also consistent. Admissibility is what guarantees A\* returns a shortest path.

Experiments on the open map:

| Heuristic | Solution found | Path length | States expanded |
|---|:--:|:--:|:--:|
| Manhattan (baseline, admissible) | yes | 23 | 125 |
| `h(n) = 0` (→ uniform-cost / BFS) | yes | 23 | 159 |
| Euclidean (admissible, looser) | yes | 23 | 132 |
| `2 × Manhattan` (inadmissible) | yes | 23 | 81 |

Shortest-path check (`maps.ALTERNATIVE`, known optimum = 4): zero, Euclidean and `2×Manhattan` all returned length 4 here. (This implementation re-opens a node when a cheaper `g` is later found, so it can recover optimality even with a mildly inflated heuristic on these small maps — see the greedy contrast below for a clean demonstration of non-optimality.)

**1. `h(n) = 0`:** A\* collapses to uniform-cost search (equivalent to BFS on unit costs). Still optimal, but it expands the most states (159) because it uses no goal information.

**2. Euclidean distance:** Still admissible (straight line ≤ grid path), still optimal, but a *looser* lower bound than Manhattan for 4-connected movement, so it guides slightly less well: 132 expanded vs Manhattan's 125.

**3. `2 × Manhattan`:** Inadmissible (it can over-estimate). It expands far fewer states (81) because it pushes hard toward the goal — but this speed is bought by **giving up the optimality guarantee**. It stayed optimal on these particular maps only because of node re-opening; in general an over-estimating heuristic can return a longer-than-shortest path.

**A\* vs greedy best-first — a clean illustration (`maps.GREEDY_TRAP`):**

```
#########
#S..#...#
#.......#
#.#.....#
#....#..#
#....#.G#
#########
```

| Algorithm | Path length | States expanded |
|---|:--:|:--:|
| A\* (balances `g` and `h`) | **10 (optimal)** | 28 |
| Greedy best-first (`h` only) | **14 (suboptimal)** | 16 |

Greedy best-first is "too aggressive": it only looks at `h`, races toward whatever cell looks closest to the goal, walks into a longer detour, and returns a 14-step path. A\* keeps the `g` term, so it refuses to abandon a cheaper partial path and returns the true 10-step shortest path. This is the concrete answer to *"what happens when the heuristic becomes too optimistic or too aggressive?"*: you trade fewer expansions for lost optimality.

## Task 7 — Evaluation of the LLM-generated agent

1. **What was correct immediately?** The overall A\* skeleton — heap frontier, `g_score`/`came_from` tables, Manhattan heuristic, and path reconstruction — was correct and idiomatic.
2. **Bugs / design problems found.** (i) The first draft pushed `(f, state)` onto the heap without a tie-breaker, which raises a `TypeError` when two entries share `f` and Python tries to compare the tuple states. (ii) It used a plain `visited` set, which is subtly wrong for A\* if a cheaper path to an already-visited node is found later. (iii) "States expanded" was ambiguous (generated vs popped).
3. **How were they discovered?** By *reading* the code before running (the missing tie-breaker and the `visited`-set issue), and by running the tests — the trivial and no-solution cases, and the BFS-length cross-check.
4. **Unfamiliar terminology / structures?** `heapq`'s lazy-deletion idiom (pushing duplicates and skipping stale pops) needed checking against a reference; it is correct but non-obvious.
5. **Did I modify it?** Yes — added the monotonic tie-breaker counter; replaced the `visited` set with the `g_score`-relaxation test; defined "expanded" precisely as *popped-and-processed*; added the greedy and multi-heuristic variants for the experiments.
6. **Most useful tests.** The *no-solution* test (guards against infinite loops) and the *A\*-length == BFS-length* cross-check (guards optimality against a trusted baseline).
7. **Could the program be trusted without testing?** No. It looked plausible and even ran on the first map, but "working output ≠ validated algorithm": the tie-breaker bug only triggers on `f` ties, and the `visited`-set optimality bug only shows on maps with competing paths.
8. **What I understood about A\* after implementing it.** That A\*'s advantage is entirely a function of heuristic quality: with `h=0` it is just BFS, and its "fewer expansions" can vanish (corridor map) or reverse into lost optimality (inadmissible/greedy). Admissibility is the precise condition separating "faster" from "faster but wrong."

## Final Reflection

1. **Why formulate the search problem before writing the algorithm?** Because the algorithm is only correct relative to a precise `(S, A, T, s0, G, c)`. Deciding that the state is just `(row, col)` and that moves cost 1 is what makes "shortest path = fewest moves" and makes Manhattan admissible. Skipping this step hides assumptions (e.g. whether diagonal moves exist) that silently change what "correct" means.

2. **In what sense is A\* "informed"?** It uses problem-specific knowledge — the heuristic estimate `h(n)` of remaining cost — to decide where to look next, rather than expanding blindly. BFS uses only `g`; A\* adds `h`, which is extra information about the goal's location.

3. **Why does the choice of heuristic matter?** It controls both efficiency and correctness. A better (but still admissible) heuristic expands fewer states while staying optimal (Manhattan < Euclidean < zero here). An inadmissible heuristic can be faster still but may return a non-shortest path. The heuristic *is* the information the algorithm uses to decide where to search next.

4. **What did the LLM contribute to the engineering process?** It produced a correct-looking first implementation quickly, saving boilerplate, and surfaced the idiomatic `heapq` pattern. It did **not** contribute the problem formulation, the test design, or the correctness judgement.

5. **What could go wrong if an engineer accepted LLM code without testing it?** Exactly the bugs above would ship: a crash on `f`-ties, and — worse, because it is silent — a sub-optimal path on maps with competing routes. The program would still "run" and "produce a path," which is precisely the trap: *working output is not a validated algorithm.*
